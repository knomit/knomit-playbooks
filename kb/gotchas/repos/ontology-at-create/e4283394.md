# A repo's ontology is set when knomit creates it, by the create mode: clone and subscribe take it from the remote and refuse ontology_preset and ontology_yaml, and only clone brings a template's skills, recipes and trigger scripts

- `clone` and `subscribe` take the ontology from the remote branch's `.knomit/ontology.yaml`. A request that also names `ontology_preset` or `ontology_yaml` is refused, so put the template's ontology in the git repo BEFORE creating the knomit repo from it.
- `custom` writes only the `ontology_yaml` you pass. A template's skills, recipes and trigger scripts are files beside the ontology, so a template that has them (`mission`) must be created by `clone` from a git repo that holds them all.
- `custom` parses the YAML as a NEW ontology: problems that an existing repo only warns about (an attribute in the wrong scope, a bad repository-level value, a bad guidance value) are refused. Validate first with `POST /api/v1/ontologies:validate`.
- `preset` takes the copy embedded in the running knomit binary (`default` or `code`), which can differ from a template copied at another knomit commit.
- Never create a repo with the ontology id `fleet` (the `fleet` preset, or the `fleet` template as `ontology_yaml`) as a local repo: knomit treats any mounted repo with that id as the instance's fleet, and `knomit fleet register <url>` for the real fleet then fails with `already_registered`. A fleet repo is pushed to a git host and joined with `knomit fleet register`.
- A repo opens without accepting writes when its ontology is missing or does not parse; knomit never substitutes a default.

How to create: `kb/howto/templates/create-repo/`.
