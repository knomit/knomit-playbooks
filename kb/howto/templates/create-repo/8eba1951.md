# Create a repo from a template: read its files with knomit_explain, write them to their paths in a new git repo, then create the knomit repo by cloning it (or, for an ontology-only template, as a custom local repo)

**1. Read the template through knomit.** Find it with `knomit_query` (`path: "kb/templates/"`, `context: {"part": "template"}`) and explain its template fact. The walk holds its file facts, its edit facts and a `system_file` node per file; explain a node's `path` and `commit` to get the file's raw `content`.

```json knomit_explain
{"binding": "<handle>", "file": ".knomit/templates/<name>/<path>", "commit": "<the node's commit>"}
```

A file at `.knomit/templates/<name>/<path>` goes to `<path>` in the new repo. Make the edits the template's edit facts (`kb/templates/<name>/use/`) list. For a template with more than an ontology, write the files into a new git repository and commit:

```sh
git init my-repo
# write each file's content to my-repo/<path>
git -C my-repo add -A
git -C my-repo commit -m "<name> template"
```

**2. Create the knomit repo from it.** `POST /api/v1/repos` (or the web UI's create wizard). The mode decides where the ontology comes from:

| mode | ontology | use it for |
|---|---|---|
| `clone` | the remote branch's `.knomit/ontology.yaml`; `ontology_preset` and `ontology_yaml` are refused | any template, and the only route that brings skills, recipes and trigger scripts |
| `custom` | `ontology_yaml`, parsed as a NEW ontology (problems that are only warnings on an existing repo are refused) | a template whose only file under `.knomit/` is `ontology.yaml` (`general`, `coding`), never `fleet` |
| `preset` | `ontology_preset`: `default` (id `general`) or `code` (id `source-code`), the copies embedded in the running knomit binary | the built-in presets, without a template |
| `subscribe` | the remote's, read-only | following a repo, never for a new one (`kb/howto/repos/subscribe/`) |

Clone (push `my-repo` to a git host first: a local folder or `file://` URL is refused as an origin unless the instance sets `local_origin_root`):

```
POST /api/v1/repos
{"name": "my-repo", "mode": "clone", "origin": {"url": "<git URL>", "branch": "main"}}
```

Custom (ontology only):

```
POST /api/v1/repos
{"name": "my-kb", "mode": "custom", "ontology_yaml": "<the edited .knomit/ontology.yaml>"}
```

The create answers `202` with a `create_id`; `GET /api/v1/repo-creates/<create_id>` reports its progress.

**3. Follow the template's README** for anything beyond the create (hosting a mission repo, joining a fleet).

Check a new ontology first with `POST /api/v1/ontologies:validate` (the YAML file as the body): it answers `"ok": true` with the id and topics, or the diagnostics. Sharp edges: `kb/gotchas/repos/ontology-at-create/`.
