# Write a skill: .knomit/skills/<name>/SKILL.md with name (equal to the folder, kebab-case) and description frontmatter; knomit serves it from the consensus tip as an MCP prompt and through knomit_skill

**The file.** `.knomit/skills/<name>/SKILL.md` in the Agent Skills format:

```markdown
---
name: work-task
description: When to use this skill, in one or two sentences.
---

# Work a task

Instructions. $ARGUMENTS stands for what the caller passes.
```

- `name` is lowercase kebab-case and equals the folder name. `description` is non-empty. Other frontmatter keys are ignored.
- `$ARGUMENTS` is replaced by the caller's arguments; a body without it gets them appended as a final `Arguments: …` line.
- Every other file in the folder is a bundled file: text files are inlined with the skill up to 256 KiB in total; binaries and the overflow are listed by path.
- A malformed `SKILL.md` is skipped from every list and logged; it never breaks the others.

**How it is served.** knomit reads skills at the tip of the repo's consensus branch, never an agent branch or an experiment: a skill edited on an agent branch is served once it is merged. It serves them two ways:
- as MCP prompts (slash commands a person types), on an endpoint scoped to the repo or a lens;
- through the `knomit_skill` tool, which a model calls itself: without `name` it lists the skills, with `name` it returns the body and bundled files.

```json knomit_skill
{"binding": "<handle>", "name": "work-task"}
```

knomit copies skills into no harness folder. Which repo's skills a binding gets: `kb/gotchas/skills/write-repo-only/`.

**Write call skeletons into the skill.** A skill that asks for a knomit call should spell out its exact arguments as a JSON block, required arguments included: `knomit_learn` refuses a call without `moment_name` ("moment_name is required"), and a session that knows only the tool's name does not know that.
